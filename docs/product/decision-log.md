# Product Decision Log — folio-lab

บันทึกการตัดสินใจเชิงผลิตภัณฑ์ที่ "ตัดสินแล้ว" ของ PO — เป็นแหล่งอ้างอิงเดียวว่ากฎไหนมีผลอยู่

## กติกา (อ่านก่อนเขียน)

1. **Append-only** — ห้ามแก้ entry เก่า การกลับคำ/ปรับกฎคือ entry **ใหม่** แล้วเปลี่ยนเฉพาะช่อง
   `สถานะ` ของอันเก่าเป็น `♻ Superseded by PD-xxx` (แก้ได้ช่องเดียวนั้นเท่านั้น)
2. **เลขรันต่อเนื่อง** — ก่อนเขียน entry ใหม่ ให้เลื่อนลงอ่าน entry ล่างสุดเพื่อดูเลขล่าสุด
   (project นี้ไม่มีสคริปต์จองเลข — ไฟล์นี้คือ ledger)
3. **1 entry = 1 การตัดสินใจ** ที่ระบุได้ว่า "ทำอะไร" และ "เพราะอะไร" — ถ้าเขียนแล้วอ่านไม่ออกว่า
   ตัดสินอะไร แปลว่ายังไม่ใช่การตัดสินใจ ให้ไปเป็น Open Question ใน epic แทน
4. **อ้างกลับ** — story card ที่ได้รับผลต้องอ้าง `PD-###` ใน Traceability/Change Log
5. เมื่อไฟล์นี้ยาวเกิน ~100 entry ค่อยแยก volume เก่าเป็นไฟล์ archive (ตอนนั้นไฟล์ archive = immutable)

## Template

```markdown
### PD-NNN — <หัวข้อสั้น ๆ ภาษาไทย>

| ช่อง | ค่า |
| --- | --- |
| วันที่ | YYYY-MM-DD |
| สถานะ | ✅ Final |
| ขอบเขต | <epic-slug / ทั้ง project / สถาปัตยกรรม> |
| สรุป | <หนึ่งบรรทัดว่าตัดสินอะไร> |

**บริบท:** <ปัญหาหรือคำถามที่ทำให้ต้องตัดสิน>

**การตัดสินใจ:** <กฎที่มีผลจากนี้ไป — เขียนเป็นสภาพปลายทาง ไม่ใช่เล่า diff>

**เหตุผล:** <ทำไมเลือกทางนี้ ไม่เลือกทางอื่น>

**ผลที่ตามมา:** <สิ่งที่ต้องทำ/เปลี่ยนตาม — การ์ดไหน ไฟล์ไหน>
```

### PD-002 — Anchor=Route + StubProvider แทนการมี prototype tree แยก

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | ทั้ง project · สถาปัตยกรรม |
| สรุป | ไม่มีโฟลเดอร์ prototype แยก — story ผูกกับ route จริงใน `src/` โดยใช้ StubProvider เป็นข้อมูลจำลอง |

**บริบท:** UOMS มี `prototypes/` แยกจาก `src/` เพื่อให้ PO validate UI กับผู้ใช้ก่อนที่ dev จะลงมือ
project นี้คนเขียน spec กับคนเขียนโค้ดคือคนเดียวกัน การทำ UI สองรอบจึงเป็นงานซ้ำ

**การตัดสินใจ:** story ทุกใบผูกกับ **route จริง** ใน `src/app/` และเลือก **data mode** ได้สองแบบ:
`stub` (ข้อมูลจำลองแบบ offline ผ่าน `StubProvider` ซึ่ง implement สัญญา `PriceProvider` เดียวกับของจริง)
หรือ `live` (adapter จริง) หลักการ Anchor เปลี่ยนจาก "ต้นแบบถูกเสมอ" เป็น **Anchor=Route**:
เมื่อ spec กับ route ไม่ตรงกัน ให้ตัดสินว่าฝั่งไหนถูกแล้วแก้อีกฝั่งใน session เดียวกัน — ห้ามปล่อยให้ต่างกัน

**เหตุผล:** StubProvider ให้ประโยชน์เดียวกับ prototype (เดินจอได้ก่อนมีข้อมูลจริง, เดโมได้ทุกเมื่อ,
ไม่พึ่ง network) โดยไม่ต้องสร้าง UI สองชุด และเพราะมันใช้สัญญาเดียวกับ provider จริง โค้ดที่เขียนตอน stub
คือโค้ดที่จะ ship จริง ไม่ใช่ของทิ้ง

**ผลที่ตามมา:** R9 ของ skill เปลี่ยนจาก "mock limitation" เป็น **"stub limitation"** — ทุกอย่างที่
StubProvider ไม่จำลอง (rate limit, สัญลักษณ์ที่ไม่มีจริง, ความลึกข้อมูล, เน็ตช้า) ต้องเขียนกำกับในการ์ด
ว่าเป็นเรื่องของข้อมูลจริง

### PD-004 — กติกาความถูกต้องของข้อมูลราคาและผลตอบแทน

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | foundation · สถาปัตยกรรม |
| สรุป | ชุดกฎที่ทำให้ตัวเลขถูกต้องแม้ราคาปรับย้อนหลังได้: เก็บผลตอบแทนไม่ใช่ราคา, อัตราส่วนจาก batch เดียวกัน, เดือนปิดเท่านั้น, ดึงเผื่อหนึ่งเดือน, rf เป็นชุดรายเดือน freeze |

**บริบท:** ราคาปิดแบบปรับปันผลของอดีตเปลี่ยนได้ทุกครั้งที่มีปันผลรอบใหม่ แต่อัตราส่วนระหว่างสองเดือน
ในชุดเดียวกันไม่เปลี่ยน และ audit รอบ S1 พบว่าค่า risk-free คงที่ตัวเดียว fit ค่าอ้างอิง Sharpe/Sortino
ของทั้งพอร์ตและตัวเทียบพร้อมกันไม่ได้ รวมถึงพบความกำกวมเรื่องเดือนแรกของช่วง

**การตัดสินใจ:** (1) คลังเก็บ**ผลตอบแทนรายเดือน** ไม่เก็บราคา — เดือนที่ปิดแล้วถาวร เดือนที่เพิ่งปิด
ใน 7 วันปฏิทินแรกหมดอายุ 24 ชั่วโมง (2) อัตราส่วนผลตอบแทนคำนวณจากราคาที่ดึงมา**รอบเดียวกัน**เท่านั้น
(3) เดือนที่ยังไม่ปิดไม่เข้าระบบตั้งแต่ชั้นแปลงข้อมูล (4) การดึงราคา**เผื่อหนึ่งเดือนก่อนช่วงที่ขอ**
เพื่อให้เดือนแรกของช่วงมีผลตอบแทน (5) อัตราปราศจากความเสี่ยงใช้**ชุดรายเดือนที่ freeze** (T-Bill 3 เดือน)
บันทึกมาพร้อม fixture ไม่ใช่ค่าคงที่ และไม่ดึงสดจนกว่าเฟส 4

**เหตุผล:** ทุกข้อมาจากคุณสมบัติจริงของข้อมูล ไม่ใช่รสนิยม — เก็บราคาแล้วอ้างว่าถาวรคือบั๊กที่รอวันแสดงตัว
ส่วน rf คงที่จะทำให้ golden test unsatisfiable ทั้งที่โค้ดถูก

**ผลที่ตามมา:** BR-CCH-01..03, BR-NRM-04..05, BR-PRV-10, BR-FND-03, BR-ENG-11 ในการ์ด US-01..04
และชุด fixture ต้องมี RF series (ROADMAP ภาคผนวก A)

### PD-011 — สลับลำดับ ทำเฟส 3 (ตลาดไทย) ก่อนเฟส 2 และเรียงภายในเฟส 3 ใหม่

**บริบท:** หลังปิดเฟส 1 พบสองอย่างที่เปลี่ยนสมมติฐานของแผนเดิม (1) หุ้นไทยใช้ได้แล้วจริงผ่านแหล่งข้อมูล
ปัจจุบันโดยเติม `.BK` ท้ายสัญลักษณ์ ทดสอบกับ PTT.BK และ CPALL.BK แล้วได้ข้อมูลครบ (2) อัตราแลกเปลี่ยน
เงินบาทต่อดอลลาร์ก็อยู่บนแหล่งเดิมเช่นกัน (สัญลักษณ์ `THB=X` ย้อนหลังครบ 174 เดือน) แปลว่างานสกุลเงิน
ไม่ต้องต่อแหล่งข้อมูลใหม่เลย

ผลข้างเคียงที่สำคัญ: เพราะหุ้นไทยใช้ได้แล้ว ผู้ใช้จึงผสมหุ้นไทยกับสินทรัพย์สกุลดอลลาร์ได้ตั้งแต่วันนี้
และ**ได้ตัวเลขที่ผิด** เพราะระบบบวกผลตอบแทนคนละสกุลเงินตรง ๆ โดยไม่แปลงค่าเงิน — ขัดกับหลัก
"เลขเชื่อถือได้" ที่เป็นเสาหลักของโปรเจกต์ และเป็นข้อบกพร่องที่มีอยู่แล้ว ไม่ใช่ความเสี่ยงในอนาคต

**การตัดสินใจ:** (1) ทำ**เฟส 3 ก่อนเฟส 2** — ตรวจแล้วว่าเฟส 3 ไม่พึ่งงานใดในเฟส 2 และการเลื่อนเฟส 2
ไม่ทำให้ต้องรื้องานเฟส 3 ทำใหม่ (2) เรียงภายในเฟส 3 ใหม่เป็น: **สกุลเงิน + หุ้นไทยอย่างเป็นทางการ →
spike กองทุนไทยและเงินเฟ้อ → กองทุนไทย + เงินเฟ้อ** (3) กฎเดิมที่ว่า "เฟส 3 ห้ามเขียน spec ก่อน spike"
**ยังอยู่ แต่ใช้เฉพาะส่วนที่ยังไม่รู้แหล่งข้อมูล** — ส่วนสกุลเงินกับหุ้นไทยพิสูจน์แหล่งข้อมูลแล้วในวันนี้
จึงเขียน spec ได้ทันที ส่วนกองทุนไทย (ก.ล.ต.) และดัชนีราคาผู้บริโภคยังต้อง spike ก่อน

**เหตุผล:** เฟส 3 คือสิ่งที่ทำให้โปรเจกต์นี้ไม่ใช่ของลอกเลียน ส่วนเฟส 2 เป็นความสามารถที่เครื่องมือ
มาตรฐานมีอยู่แล้ว · ต้นทุนเฟส 3 ลดลงจากที่ประเมินไว้เพราะสองข้อค้นพบข้างบน · และการเรียงใหม่ทำให้
งานที่ปิดข้อบกพร่องเรื่องความถูกต้องมาก่อนงานที่เสี่ยงต่อความไม่แน่นอนของแหล่งข้อมูล

**ผลที่ตามมา:** SESSION-PLAN จัดกลุ่มใหม่ (S9–S13 = ตลาดไทย · S14–S16 = เทียบพอร์ตและเงินเข้าออก ·
S17 เป็นต้นไปเลื่อนตาม) · ROADMAP ระบุลำดับที่ใช้จริง · epic `thai-market` เขียนเฉพาะการ์ดที่พิสูจน์
แหล่งข้อมูลแล้ว ส่วนที่เหลือรอ spike

### PD-015 — เมื่อมีเงินเข้าออก ให้แสดงผลตอบแทนสองค่าพร้อมป้ายกำกับ

**บริบท:** เมื่อพอร์ตมีเงินเข้าออกระหว่างทาง คำว่า "ผลตอบแทนต่อปี" มีสองความหมายที่ต่างกันจริง —
ค่าหนึ่งวัดฝีมือของพอร์ตโดยไม่สนจังหวะที่ใส่เงิน อีกค่าวัดว่าเงินของผู้ใช้โตกี่เปอร์เซ็นต์ต่อปี
ทั้งสองถูกคนละแบบ และต่างกันได้มาก: พอร์ตที่ผลตอบแทนสองเดือนเป็น `+50%` แล้ว `−20%` ให้ผลตอบแทน
ของพอร์ต `+20%` แต่คนที่ใส่เงินก้อนที่สองก่อนเดือนที่แย่พอดี ได้ผลตอบแทนของเงินตัวเองเป็น `0%`

**การตัดสินใจ:** (1) **ชุดผลตอบแทนรายเดือนของพอร์ตไม่ขึ้นกับเงินเข้าออก** — ความผันผวน ช่วงขาดทุน
Sharpe Sortino ปีดี/แย่ที่สุด และผลตอบแทนต่อปีแบบทบต้น ใช้นิยามเดิมทุกตัว ไม่มีข้อยกเว้น
(2) **มูลค่าสุดท้าย**มาจากเส้นมูลค่าที่รวมเงินเข้าออกแล้ว (3) พอร์ตที่มีเงินเข้าออกได้เพิ่มสองค่า:
**เงินที่ใส่ทั้งหมด** และ **ผลตอบแทนต่อปีถ่วงน้ำหนักเงิน** (4) **ทั้งสองนิยามต้องมีป้ายกำกับที่บอกว่า
วัดอะไร พร้อมคำอธิบายไทยที่อธิบายความต่าง** — ห้ามแสดงค่าเดียวเคียงข้างมูลค่าสุดท้ายที่มีเงินเข้าออก
โดยไม่ระบุ (5) ค่าที่หาไม่ได้คืนไม่มีค่า ไม่ใช่ 0

**เหตุผล:** ทางเลือกที่ง่ายกว่าคือแสดงค่าเดียว แต่ทั้งสองทางที่ง่ายนั้นเสียหายคนละแบบ — แสดงเฉพาะ
ผลตอบแทนของพอร์ตแล้ววางข้างมูลค่าสุดท้ายที่โตจากการทยอยใส่เงิน ทำให้ผู้ใช้เข้าใจว่าเงินตัวเองโตเท่านั้น
ซึ่งเป็นความเสียหายระดับ P0 ตามหลัก "เลขต้องเชื่อถือได้" · ส่วนการสลับไปแสดงเฉพาะค่าถ่วงน้ำหนักเงิน
ทำให้เทียบพอร์ตที่ทยอยลงทุนกับพอร์ตที่ลงทีเดียวไม่ได้ เพราะเสียค่าที่วัดฝีมือพอร์ตล้วน ๆ ไป
· การแสดงสองค่าพร้อมป้ายกำกับแพงกว่านิดเดียวแต่ไม่ทำให้ใครอ่านผิด และยังรักษาความสามารถ
ในการเทียบข้ามพอร์ตไว้ครบ

**ผลที่ตามมา:** US-18 ถือกฎชุดนี้ทั้งหมดพร้อมเคสคำนวณมือที่พิสูจน์ว่าสองนิยามต่างกันจริง ·
epic §9 มีกฎ BR-CMP-10 ถึง BR-CMP-14 · ทะเบียนศัพท์การเงินเพิ่มสองรายการพร้อมสูตรและหน่วยเวลา ·

### PD-016 — วิธีกระจายเงินที่ใส่เพิ่ม ให้ผู้ใช้เลือกเอง

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-30 |
| สถานะ | ✅ Final |
| ขอบเขต | compare-cashflows · นิยาม metric |
| สรุป | เงินที่ใส่เพิ่มกระจายได้สองแบบ — ตามสัดส่วนที่ถืออยู่ (ปริยาย) หรือตามน้ำหนักเป้าหมาย — เพราะสองแบบตอบคนละคำถาม |

**บริบท:** BR-CMP-59 ที่เขียนไว้ตอน S14 บอกให้เงินที่ใส่เพิ่มกระจายเข้าสินทรัพย์**ตามน้ำหนักเป้าหมาย**
อย่างเดียว ตอนลงมือทำที่ S15b พบว่ากฎข้อนี้ขัดกับกฎอื่นที่เป็น P0 ทั้งหมด — การกระจายตามน้ำหนัก
เป้าหมายคือการดึงน้ำหนักกลับเข้าเป้า ซึ่ง**เป็นการปรับสมดุลโดยนิยาม** จึงทำให้ชุดผลตอบแทนรายเดือน
เปลี่ยน ขัดกับ BR-CMP-39/40 และทำให้ AC-CMP-26 (พอร์ตสินทรัพย์ชุดเดียวกันต้องได้ผลตอบแทนต่อปี
แบบทบต้นเท่ากัน) เป็นจริงไม่ได้ · ตัวกฎเองก็ขัดกันเอง เพราะระบุต่อว่า "การใส่เงินไม่นับเป็นการปรับสมดุล"

ตัวอย่างที่ทำให้เห็นชัด — สินทรัพย์ A กับ B เป้าหมาย 50/50 ตั้งไม่ปรับสมดุล เดือนที่ 1 A `+100%`
B `0%` เดือนที่ 2 A `0%` B `+100%` · ลงทีเดียวได้ชุดผลตอบแทน `[+50%, +33.3%]` · ทยอยลงทุนที่
กระจายตามสัดส่วนที่ถืออยู่ได้ `[+50%, +33.3%]` เท่ากันเป๊ะ · แต่ทยอยลงทุนที่กระจายตามน้ำหนักเป้าหมาย
ได้ `[+50%, +40%]` ต่างออกไป เพราะเงินก้อนใหม่ไปซื้อตัวที่น้ำหนักตกต่ำกว่าเป้ามากกว่า

**การตัดสินใจ:** **ให้ผู้ใช้เลือกวิธีกระจายเองในฟอร์ม** เป็นค่าระดับพอร์ต
(1) **ตามสัดส่วนที่ถืออยู่** — ค่าปริยาย · ทุกสินทรัพย์ถูกคูณเท่ากัน สัดส่วนไม่ขยับ ชุดผลตอบแทน
จึงไม่ถูกแตะ และเทียบ "ลงทีเดียว vs ทยอยลงทุน" ได้โดยเปลี่ยนตัวแปรเดียว
(2) **ตามน้ำหนักเป้าหมาย** — จำลองพฤติกรรมจริงของคนที่ซื้อตามสัดส่วนเป้าหมายทุกงวด ·
เมื่อเลือกแบบนี้ ชุดผลตอบแทนเปลี่ยนได้ และนั่นคือพฤติกรรมที่ถูกต้องของวิธีนี้

### PD-026 — ถอนคำอ้างกองทุนไทยออกจากข้อความที่ผู้ใช้เห็น แล้วทำการ์ดพรีวิวลิงก์

| สถานะ | ✅ Final |
| ขอบเขต | social-preview · US-36 · **ถอนคำอ้างที่ ship ไปแล้ว** |
| สรุป | ข้อความที่ผู้ใช้เห็นพูดได้เฉพาะสิ่งที่ ship แล้ว — ตัด "กองทุนไทย" ออกทั้งสามจุด · และเว็บส่งข้อมูลพรีวิวพร้อมภาพหน้าจอจริงออกไปเวลาถูกแชร์ |

**บริบท:** ตอนเตรียมเอาลิงก์ไปแชร์พบสองเรื่องพร้อมกัน · หนึ่ง — หน้าเว็บไม่ได้ส่งข้อมูลพรีวิวออกไปเลย
แพลตฟอร์มจึงวาดเป็นกล่องเทาที่มีแค่คำว่า `folio-lab` · สอง — ข้อความที่ผู้ใช้เห็นสามจุดยังบอกว่า
เครื่องมือนี้รวม "กองทุนไทย" ได้ ทั้งที่ **PD-012** พักความสามารถนี้ไว้ตั้งแต่ 2026-07-30 เพราะแหล่งข้อมูล
ปัจจุบันไม่มีกองทุนไทยเลย · สองเรื่องนี้แยกกันไม่ได้ เพราะคำอธิบายพรีวิวดึงมาจากข้อความชุดเดียวกัน —
ถ้าทำการ์ดพรีวิวโดยไม่แก้คำอ้าง เท่ากับขยายคำอ้างที่ไม่จริงให้กว้างขึ้นอีก

| จุดที่พูดเกินจริง | ไฟล์ |
| --- | --- |
| คำอธิบายของหน้าเว็บ (ที่แพลตฟอร์มดึงไปแสดง) | `src/app/layout.tsx` |
| ประโยคแนะนำใต้ชื่อเครื่องมือ (ไทย) | `src/i18n/locales/th.json` · `app.tagline` |
| ประโยคแนะนำใต้ชื่อเครื่องมือ (อังกฤษ) | `src/i18n/locales/en.json` · `app.tagline` |

**การตัดสินใจ:**
1. **ข้อความที่ผู้ใช้เห็นพูดได้เฉพาะความสามารถที่ ship แล้ว** — ระหว่างที่กองทุนรวมไทยยังพักตาม PD-012
   ทั้งสามจุดพูดว่า "หุ้นไทยและ ETF ต่างประเทศ" และมีบรรทัดบอกสถานะจริงว่า
   **"กองทุนรวมไทยยังไม่เปิดใช้ · รอสิทธิ์เข้าถึงข้อมูลจาก ก.ล.ต."** ไม่ใช่ตัดทิ้งเงียบ ๆ ·
   ถ้อยคำต้อง**ไม่ใช้คำว่า "กำลังพัฒนา"** เพราะ **BR-DMO-06** (US-11) ห้ามคำนั้นบนหน้าแรกไว้แล้ว —
   ตอนนั้นมันหมายถึงทั้งเครื่องมือยังไม่เสร็จ ซึ่งเป็นสัญญาณคนละเรื่องกับฟีเจอร์เดียวที่ยังไม่เปิด ·
   การระบุ**เหตุผล**ที่ยังไม่เปิด (ติดสิทธิ์เข้าถึงข้อมูล ไม่ใช่ยังทำไม่ได้) ชัดกว่าและไม่ชนกฎเดิม
2. **เว็บส่งข้อมูลพรีวิวออกไปครบ** (หัวเรื่อง · คำอธิบาย · ภาพ · ชื่อเว็บ) ตั้งที่ layout ราก เพื่อให้ตกทอด
   ถึงทุก route — คนแชร์ลิงก์หน้าไหนก็ได้การ์ดเดียวกัน
3. **ภาพพรีวิวเป็นภาพหน้าจอผลลัพธ์จริงขนาด 1200 × 630** ไม่ใช่ภาพวาดหรือภาพจำลอง
4. **ที่อยู่เว็บฐานมีค่าเดียวในระบบ** — ใช้ค่าเดียวกับที่ `scripts/verify-production.mjs` ใช้อยู่

**เหตุผล:** คนที่เห็นลิงก์ตัดสินใจภายในไม่กี่วินาทีจากภาพและข้อความเท่านั้น · กล่องเปล่าทำให้ลิงก์ที่
ควรเป็นจุดแข็งดูเหมือนลิงก์เสีย · ส่วนเรื่องคำอ้าง — คนที่กดเข้ามาแล้วลองค้นกองทุนจะเจอช่องว่างทันที

ติดที่ยังทำไม่ได้" เป็นเรื่องเล่าที่ดีกว่าสำหรับคนอ่าน ไม่ใช่ข้อเสีย

**ทางที่ไม่เลือก:**
- **ตัดคำว่ากองทุนไทยทิ้งเฉย ๆ** — เสียข้อมูลว่าสถาปัตยกรรมเตรียมไว้แล้ว ซึ่งเป็นจริงและมีค่า
- **ทำภาพพรีวิวเป็นการ์ดออกแบบ** (สร้างภาพจากข้อความตอน build) — อ่านง่ายกว่าเวลาย่อ แต่ไม่ได้
  พิสูจน์ว่ามีของจริง · เลือกภาพหน้าจอจริงเพราะคนดูต้องเห็นว่าเครื่องมือทำงานได้ ไม่ใช่แค่มีโลโก้สวย
- **ทำพรีวิวแยกภาษา** — ต้องเปลี่ยนโครงสร้าง route ให้มี URL ต่อภาษาก่อน · ตอนนี้หนึ่ง URL เสิร์ฟ
  สองภาษาโดยสลับฝั่ง browser ตัวดึงข้อมูลของแพลตฟอร์มไม่รัน JavaScript จึงเห็นภาษาไทยเสมอ
  การประกาศว่ามีเวอร์ชันอังกฤษจะชี้ไปยัง URL ที่ไม่มีอยู่

**ผลที่ตามมา:**

- ประโยคแนะนำอยู่ในชั้น i18n แต่คำอธิบายพรีวิวเป็นข้อความคงที่ฝั่งเซิร์ฟเวอร์ที่ i18n เข้าไม่ถึง —
  **สองที่นี้ต้องแก้พร้อมกันเสมอ** บันทึกไว้เป็นกฎร่วมใน epic §9
- เมื่อกองทุนรวมไทยเปิดใช้ได้จริง ต้องแก้ข้อความทั้งสามจุดพร้อมกัน และบันทึกเป็น PD ใหม่ที่ทับ entry นี้
- แพลตฟอร์มจำการ์ดเก่าไว้ — หลัง deploy ต้องบังคับให้ดึงใหม่ก่อนเอาลิงก์ไปใช้จริง

### PD-027 — วัดผลการใช้งานด้วย GA4 โดยส่งรูปร่างไม่ส่งค่า

**บริบท:** โปรเจกต์นี้มีบทบาทที่สองคือเป็นผลงานประกอบการสมัครงาน แต่ตอนนี้ไม่มีเครื่องมือวัดใด ๆ
เลย จึงพูดถึงการใช้งานจริงไม่ได้สักคำ · ประเด็นสำคัญคือ **จำนวนผู้เข้าชมของเว็บส่วนตัวแทบไม่มี
น้ำหนัก** สิ่งที่มีน้ำหนักคืออัตราที่คนเข้ามาแล้วได้ใช้ของจริง ซึ่งไม่ได้มาฟรีจากการฝังสคริปต์ —
ต้องนิยามเหตุการณ์ที่จะวัดเอง

**การตัดสินใจ:**

1. **ใช้ GA4** ฝังเองด้วย `next/script` ไม่เพิ่ม dependency
2. **ส่งรูปร่าง ไม่ส่งค่า** — จำนวนพอร์ต สกุลเงินฐาน ช่วงกี่ปี มีเงินเข้าออกไหม ส่งได้ ·
   **จำนวนเงินและรายชื่อสัญลักษณ์ที่ผู้ใช้กรอก ห้ามส่งเด็ดขาด**
3. **ตั้งความยินยอมเป็นปฏิเสธทั้งหมดก่อนตั้งค่าใด ๆ เสมอ** — ได้ตัวเลขรวมโดยไม่วางคุกกี้ ·
   แบนเนอร์ขอความยินยอมเป็นการ์ดแยกในอนาคต
4. **ชั้นใหม่ในสัญญาสถาปัตยกรรม** — `src/data/analytics/**` เป็นเจ้าของการคุยกับบริการวัดผล ·

   ต้องมีที่เดียวที่ปิดสวิตช์ได้

6. **รหัสวัดผลเป็นของสาธารณะ** ใช้ชื่อตัวแปรที่ขึ้นต้นด้วย `NEXT_PUBLIC_` ได้และควรเป็นแบบนั้น

**เหตุผล:** เลือก GA4 ทั้งที่ตัวเลือกอื่นไม่ต้องมีแบนเนอร์ความยินยอม เพราะ GA4 เป็นชื่อที่คนคัด

ข้อ 2 ไม่ได้มาจากข้อบังคับใด แต่มาจากหลักว่าอย่าเก็บสิ่งที่ไม่ได้ใช้ตอบคำถาม จำนวนเงินไม่ช่วยตอบ

### PD-028 — แยกค่าเริ่มต้นของความยินยอมตามภูมิภาค แทนการปฏิเสธทุกที่

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-08-03 |
| สถานะ | ✅ Final |
| ขอบเขต | usage-analytics · แทนที่ข้อ 3 ของ [PD-027](#pd-027--วัดผลการใช้งานด้วย-ga4-โดยส่งรูปร่างไม่ส่งค่า) |
| สรุป | ปฏิเสธความยินยอมเฉพาะเขตที่กฎหมายบังคับให้ขอก่อน ที่เหลืออนุญาตเฉพาะการวัดผลการใช้งาน · โฆษณาปฏิเสธทุกที่เสมอ |

**บริบท:** PD-027 ข้อ 3 ตั้งความยินยอมเป็นปฏิเสธทุกกรณีเพื่อความปลอดภัย โดยเข้าใจว่าจะยังได้
ตัวเลขรวมแบบไม่มีคุกกี้ · **พอ ship จริงแล้ววัดพบว่าเข้าใจผิด** — ข้อมูลไปถึงปลายทางสำเร็จ
(ตอบกลับ `204` ทุกคำขอ) แต่**ไม่ถูกนับเข้ารายงานเลยแม้แต่รายการเดียว** เพราะข้อมูลแบบไม่มีคุกกี้
จะถูกใช้ก็ต่อเมื่อเว็บมีปริมาณมากพอให้ปลายทางสร้างแบบจำลอง ซึ่งเว็บขนาดนี้ไม่มีทางถึง

ผลคือหน้ารายงานขึ้นว่า "ยังไม่ได้รับข้อมูล" ทั้งที่ติดตั้งถูกทุกอย่าง — เท่ากับเครื่องมือวัดที่
วัดอะไรไม่ได้เลย ซึ่งไม่ตอบเหตุผลที่สร้างมันขึ้นมาตั้งแต่แรก

**การตัดสินใจ:**

1. **เขตที่กฎหมายบังคับให้ขอความยินยอมก่อน** (สหภาพยุโรป 27 ประเทศ + ไอซ์แลนด์ ลิกเตนสไตน์
   นอร์เวย์ + สหราชอาณาจักร + สวิตเซอร์แลนด์) → **ปฏิเสธทุกข้อตามเดิม**
2. **นอกเขตนั้น** → **อนุญาตเฉพาะการเก็บข้อมูลการวัดผลการใช้งาน**
3. **สิทธิ์ที่เกี่ยวกับโฆษณาปฏิเสธทุกที่เสมอ ไม่มีข้อยกเว้น** — เว็บนี้ไม่ทำโฆษณาและไม่มีแผนจะทำ
   จึงไม่มีเหตุผลให้ขอสิทธิ์ที่ไม่ได้ใช้
4. รายชื่อเขตอยู่ในโค้ดเป็นค่าคงที่ชุดเดียว ไม่กระจาย

**เหตุผล:** ทางเลือกที่พิจารณามีสาม — ทำแบนเนอร์เต็มรูปแบบ · อนุญาตทุกที่ · แยกตามภูมิภาค ·
เลือกข้อสามเพราะได้ข้อมูลจริงจากผู้ใช้ส่วนใหญ่ทันทีโดยไม่ต้องแลกกับความถูกต้องในเขตที่เข้มงวด
· การอนุญาตทุกที่จะวางคุกกี้กับผู้ใช้ยุโรปโดยไม่ขอ ซึ่งขัดกับเหตุผลเดียวกับที่ทำให้เลือก
ระดับจ่ายเงินของบริการ AI ไว้ก่อนหน้า · ส่วนแบนเนอร์เป็นทางที่ถูกที่สุดทุกภูมิภาคและยังควรทำ
แต่เป็นงานที่มีข้อความผู้ใช้สองภาษาและสถานะ UI ของตัวเอง จึงไม่ควรถูกบีบให้เสร็จในรอบนี้

**สิ่งที่ยังไม่เปลี่ยน:** ข้อ 1, 2, 4, 5, 6 ของ PD-027 ยังมีผลตามเดิมทั้งหมด —
โดยเฉพาะ **ส่งรูปร่างไม่ส่งค่า** ซึ่งไม่เกี่ยวกับความยินยอมเลย

**ผลที่ตามมา:**
- US-38 ([`stories/usage-analytics/US-38-regional-consent.md`](./stories/usage-analytics/US-38-regional-consent.md))
  ครอบการเปลี่ยนนี้ · US-37 เป็น ✅ Done แล้วจึงไม่แก้เนื้อ (R5 แถว Retraction)
- ตัวเลขจากผู้ใช้ในเขตที่ปฏิเสธจะยัง**ไม่ถูกนับ** — ตัวเลขที่ได้จึงเป็นค่าต่ำกว่าจริงเสมอ
  ใช้เป็นอัตราส่วนได้ ห้ามอ้างเป็นยอดสัมบูรณ์ (ข้อนี้ยกมาจาก PD-027 ไม่เปลี่ยน)
- **ยืนยันฝั่งเขตที่ปฏิเสธด้วยเครื่องในไทยไม่ได้** เพราะปลายทางตัดสินเขตจากที่อยู่เครือข่าย —
  ต้องเขียนข้อจำกัดนี้ไว้ในการ์ด ไม่ใช่อ้างว่าตรวจแล้ว
- เมื่อทำแบนเนอร์ขอความยินยอมจริง ต้องบันทึกเป็น PD ใหม่ที่ทับ entry นี้
