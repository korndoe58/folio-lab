# Product Decision Log — folio-lab

บันทึกการตัดสินใจเชิงผลิตภัณฑ์ที่ "ตัดสินแล้ว" ของ PO — เป็นแหล่งอ้างอิงเดียวว่ากฎไหนมีผลอยู่

## กติกา (อ่านก่อนเขียน)

1. **Append-only** — ห้ามแก้ entry เก่า การกลับคำ/ปรับกฎคือ entry **ใหม่** แล้วเปลี่ยนเฉพาะช่อง
   `สถานะ` ของอันเก่าเป็น `♻ Superseded by PD-xxx` (แก้ได้ช่องเดียวนั้นเท่านั้น)
2. **เลขรันต่อเนื่อง** — ก่อนเขียน entry ใหม่ ให้เลื่อนลงอ่าน entry ล่างสุดเพื่อดูเลขล่าสุด
   (project นี้ไม่มีสคริปต์จองเลข — ไฟล์นี้คือ ledger)
3. **1 entry = 1 การตัดสินใจ** ที่ระบุได้ว่า "ทำอะไร" และ "เพราะอะไร" — ถ้าเขียนแล้วอ่านไม่ออกว่า
   ตัดสินอะไร แปลว่ายังไม่ใช่การตัดสินใจ ให้ไปเป็น Open Question ใน epic แทน
4. **อ้างกลับ** — story card ที่ได้รับผลต้องอ้าง `PD-###` ใน Traceability/Change Log
5. เมื่อไฟล์นี้ยาวเกิน ~100 entry ค่อยแยก volume เก่าเป็นไฟล์ archive (ตอนนั้นไฟล์ archive = immutable)

## Template

```markdown
### PD-NNN — <หัวข้อสั้น ๆ ภาษาไทย>

| ช่อง | ค่า |
| --- | --- |
| วันที่ | YYYY-MM-DD |
| สถานะ | ✅ Final |
| ขอบเขต | <epic-slug / ทั้ง project / สถาปัตยกรรม> |
| สรุป | <หนึ่งบรรทัดว่าตัดสินอะไร> |

**บริบท:** <ปัญหาหรือคำถามที่ทำให้ต้องตัดสิน>

**การตัดสินใจ:** <กฎที่มีผลจากนี้ไป — เขียนเป็นสภาพปลายทาง ไม่ใช่เล่า diff>

**เหตุผล:** <ทำไมเลือกทางนี้ ไม่เลือกทางอื่น>

**ผลที่ตามมา:** <สิ่งที่ต้องทำ/เปลี่ยนตาม — การ์ดไหน ไฟล์ไหน>
```

### PD-002 — Anchor=Route + StubProvider แทนการมี prototype tree แยก

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | ทั้ง project · สถาปัตยกรรม |
| สรุป | ไม่มีโฟลเดอร์ prototype แยก — story ผูกกับ route จริงใน `src/` โดยใช้ StubProvider เป็นข้อมูลจำลอง |

**บริบท:** UOMS มี `prototypes/` แยกจาก `src/` เพื่อให้ PO validate UI กับผู้ใช้ก่อนที่ dev จะลงมือ
project นี้คนเขียน spec กับคนเขียนโค้ดคือคนเดียวกัน การทำ UI สองรอบจึงเป็นงานซ้ำ

**การตัดสินใจ:** story ทุกใบผูกกับ **route จริง** ใน `src/app/` และเลือก **data mode** ได้สองแบบ:
`stub` (ข้อมูลจำลองแบบ offline ผ่าน `StubProvider` ซึ่ง implement สัญญา `PriceProvider` เดียวกับของจริง)
หรือ `live` (adapter จริง) หลักการ Anchor เปลี่ยนจาก "ต้นแบบถูกเสมอ" เป็น **Anchor=Route**:
เมื่อ spec กับ route ไม่ตรงกัน ให้ตัดสินว่าฝั่งไหนถูกแล้วแก้อีกฝั่งใน session เดียวกัน — ห้ามปล่อยให้ต่างกัน

**เหตุผล:** StubProvider ให้ประโยชน์เดียวกับ prototype (เดินจอได้ก่อนมีข้อมูลจริง, เดโมได้ทุกเมื่อ,
ไม่พึ่ง network) โดยไม่ต้องสร้าง UI สองชุด และเพราะมันใช้สัญญาเดียวกับ provider จริง โค้ดที่เขียนตอน stub
คือโค้ดที่จะ ship จริง ไม่ใช่ของทิ้ง

**ผลที่ตามมา:** R9 ของ skill เปลี่ยนจาก "mock limitation" เป็น **"stub limitation"** — ทุกอย่างที่
StubProvider ไม่จำลอง (rate limit, สัญลักษณ์ที่ไม่มีจริง, ความลึกข้อมูล, เน็ตช้า) ต้องเขียนกำกับในการ์ด
ว่าเป็นเรื่องของข้อมูลจริง

### PD-004 — กติกาความถูกต้องของข้อมูลราคาและผลตอบแทน

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | foundation · สถาปัตยกรรม |
| สรุป | ชุดกฎที่ทำให้ตัวเลขถูกต้องแม้ราคาปรับย้อนหลังได้: เก็บผลตอบแทนไม่ใช่ราคา, อัตราส่วนจาก batch เดียวกัน, เดือนปิดเท่านั้น, ดึงเผื่อหนึ่งเดือน, rf เป็นชุดรายเดือน freeze |

**บริบท:** ราคาปิดแบบปรับปันผลของอดีตเปลี่ยนได้ทุกครั้งที่มีปันผลรอบใหม่ แต่อัตราส่วนระหว่างสองเดือน
ในชุดเดียวกันไม่เปลี่ยน และ audit รอบ S1 พบว่าค่า risk-free คงที่ตัวเดียว fit ค่าอ้างอิง Sharpe/Sortino
ของทั้งพอร์ตและตัวเทียบพร้อมกันไม่ได้ รวมถึงพบความกำกวมเรื่องเดือนแรกของช่วง

**การตัดสินใจ:** (1) คลังเก็บ**ผลตอบแทนรายเดือน** ไม่เก็บราคา — เดือนที่ปิดแล้วถาวร เดือนที่เพิ่งปิด
ใน 7 วันปฏิทินแรกหมดอายุ 24 ชั่วโมง (2) อัตราส่วนผลตอบแทนคำนวณจากราคาที่ดึงมา**รอบเดียวกัน**เท่านั้น
(3) เดือนที่ยังไม่ปิดไม่เข้าระบบตั้งแต่ชั้นแปลงข้อมูล (4) การดึงราคา**เผื่อหนึ่งเดือนก่อนช่วงที่ขอ**
เพื่อให้เดือนแรกของช่วงมีผลตอบแทน (5) อัตราปราศจากความเสี่ยงใช้**ชุดรายเดือนที่ freeze** (T-Bill 3 เดือน)
บันทึกมาพร้อม fixture ไม่ใช่ค่าคงที่ และไม่ดึงสดจนกว่าเฟส 4

**เหตุผล:** ทุกข้อมาจากคุณสมบัติจริงของข้อมูล ไม่ใช่รสนิยม — เก็บราคาแล้วอ้างว่าถาวรคือบั๊กที่รอวันแสดงตัว
ส่วน rf คงที่จะทำให้ golden test unsatisfiable ทั้งที่โค้ดถูก

**ผลที่ตามมา:** BR-CCH-01..03, BR-NRM-04..05, BR-PRV-10, BR-FND-03, BR-ENG-11 ในการ์ด US-01..04
และชุด fixture ต้องมี RF series (ROADMAP ภาคผนวก A)

**บริบท:** ตอนรัน golden tests ครั้งแรกใน S3 ค่า 8 จาก 9 กลุ่มตรงต้นแบบทันที เหลือกรณีเดียวคือเดือนที่ฟื้น
ของช่วงขาดทุน COVID: เราได้ ก.ค. 2020 (4 เดือน) ต้นแบบระบุ ส.ค. 2020 (5 เดือน) การตรวจพบว่ามูลค่าพอร์ต
ณ สิ้น ก.ค. 2020 อยู่เหนือจุดสูงสุดเดิมของ ธ.ค. 2019 เพียง **0.0034%** ส่วนความลึก (−17.36%) เดือนเริ่มตก
และเดือนต่ำสุด ตรงกับต้นแบบทุกค่า

**การตัดสินใจ:** ตารางช่วงขาดทุนใน ROADMAP ภาคผนวก A **ยึดค่าที่คำนวณจากข้อมูลที่เรา freeze ไว้**
(แถวที่ 2 = ก.ค. 2020 / 4 เดือน) พร้อมหมายเหตุกำกับว่าต่างจากต้นแบบเพราะเหตุใด สูตรของชั้นคำนวณไม่แก้

**เหตุผล:** ระยะ 0.0034% เล็กกว่าความต่างตามปกติของราคาปิดที่ปรับปันผลแล้วระหว่างผู้ให้บริการข้อมูล
สองเจ้า การแก้สูตรให้ได้เดือนตรงกับต้นแบบเท่ากับปรับจูนเครื่องคำนวณให้เข้ากับข้อมูลของเจ้าหนึ่ง
ซึ่งจะทำให้เลขผิดเมื่อสลับแหล่งข้อมูล — ตรงข้ามกับเป้าหมาย "เลขเชื่อถือได้" สิ่งที่ชุดทดสอบควรพิสูจน์คือ
**นิยามถูกต้องเมื่อใช้กับข้อมูลที่เราใช้จริง** ไม่ใช่ผลลัพธ์ตรงกับผู้ให้บริการรายใดรายหนึ่ง

**ผลที่ตามมา:** แถวที่ 2 ของตารางช่วงขาดทุนในภาคผนวก A + หมายเหตุกำกับ · ค่าคาดหวังใน golden test
ของ US-04 · เมื่อเปลี่ยนแหล่งข้อมูลหรือ freeze ใหม่ในอนาคต ต้องตรวจตารางนี้อีกครั้งและบันทึกส่วนต่างแบบเดียวกัน
