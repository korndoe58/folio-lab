# Product Decision Log — folio-lab

บันทึกการตัดสินใจเชิงผลิตภัณฑ์ที่ "ตัดสินแล้ว" ของ PO — เป็นแหล่งอ้างอิงเดียวว่ากฎไหนมีผลอยู่

## กติกา (อ่านก่อนเขียน)

1. **Append-only** — ห้ามแก้ entry เก่า การกลับคำ/ปรับกฎคือ entry **ใหม่** แล้วเปลี่ยนเฉพาะช่อง
   `สถานะ` ของอันเก่าเป็น `♻ Superseded by PD-xxx` (แก้ได้ช่องเดียวนั้นเท่านั้น)
2. **เลขรันต่อเนื่อง** — ก่อนเขียน entry ใหม่ ให้เลื่อนลงอ่าน entry ล่างสุดเพื่อดูเลขล่าสุด
   (project นี้ไม่มีสคริปต์จองเลข — ไฟล์นี้คือ ledger)
3. **1 entry = 1 การตัดสินใจ** ที่ระบุได้ว่า "ทำอะไร" และ "เพราะอะไร" — ถ้าเขียนแล้วอ่านไม่ออกว่า
   ตัดสินอะไร แปลว่ายังไม่ใช่การตัดสินใจ ให้ไปเป็น Open Question ใน epic แทน
4. **อ้างกลับ** — story card ที่ได้รับผลต้องอ้าง `PD-###` ใน Traceability/Change Log
5. เมื่อไฟล์นี้ยาวเกิน ~100 entry ค่อยแยก volume เก่าเป็นไฟล์ archive (ตอนนั้นไฟล์ archive = immutable)

## Template

```markdown
### PD-NNN — <หัวข้อสั้น ๆ ภาษาไทย>

| ช่อง | ค่า |
| --- | --- |
| วันที่ | YYYY-MM-DD |
| สถานะ | ✅ Final |
| ขอบเขต | <epic-slug / ทั้ง project / สถาปัตยกรรม> |
| สรุป | <หนึ่งบรรทัดว่าตัดสินอะไร> |

**บริบท:** <ปัญหาหรือคำถามที่ทำให้ต้องตัดสิน>

**การตัดสินใจ:** <กฎที่มีผลจากนี้ไป — เขียนเป็นสภาพปลายทาง ไม่ใช่เล่า diff>

**เหตุผล:** <ทำไมเลือกทางนี้ ไม่เลือกทางอื่น>

**ผลที่ตามมา:** <สิ่งที่ต้องทำ/เปลี่ยนตาม — การ์ดไหน ไฟล์ไหน>
```

### PD-001 — รับ practice story-first ฉบับขยายถึง ship

| ช่อง | ค่า |

| วันที่ | 2026-07-29 |

| สรุป | ใช้ practice story-first แบบเดียวกับ UOMS แต่ขยาย skill ให้ครอบถึง implement + verify + ship |

**บริบท:** practice `write-story-epic` ที่ใช้กับ UOMS จบที่ prototype เพราะมีทีม dev รับช่วงต่อ
project นี้ไม่มีทีม — ถ้าใช้ของเดิมตรง ๆ จะมี spec สวยแต่ไม่มีกติกาว่าโค้ดที่เขียนเองต้องผ่านอะไรถึงเรียกว่าเสร็จ

**การตัดสินใจ:** ใช้ skill ฉบับปรับที่ `.claude/skills/write-story-epic/SKILL.md` ซึ่งมี 2 โหมด —
MODE A เขียน spec, MODE B implement — และเพิ่มกฎฝั่ง develop สามข้อ: **R15 layering**
(engine pure / adapter คุยโลกนอก / UI ไม่คำนวณเอง), **R16 golden numbers** (แตะ engine ต้อง golden เขียว;
metric ใหม่ต้องมี test + สูตรที่เขียนไว้ + tooltip ไทย), **R17 evidence-Done** (✅ ได้ต่อเมื่อ guards เขียว +
เดิน route จริง + มี screenshot) กฎ R1–R14 ยกมาจาก UOMS โดยปรับให้เข้ากับ codebase นี้
ตัด R8 RBAC ออกเพราะไม่มีระบบผู้ใช้ (แทนด้วยกฎ no-auth invariant)

**เหตุผล:** กฎที่ทำให้ UOMS ไม่พังคือ "อย่าแก้ของที่ commit แล้ว" กับ "เขียนสภาพปลายทาง ไม่ใช่เล่า diff" —
ทั้งคู่ใช้ได้กับ project เดี่ยวเหมือนกัน ส่วนสิ่งที่ขาดคือประตูออกฝั่งโค้ด จึงเติม R15–R17 เข้าไป

**ผลที่ตามมา:** ทุก session ต้องอ่าน SKILL.md ก่อนเริ่ม; `CLAUDE.md` ชี้ไปที่ skill; skill เก็บใน
`.claude/` ซึ่ง gitignore ไว้ (เป็นเครื่องมือส่วนตัว ไม่ใช่ส่วนหนึ่งของ repo สาธารณะ)

### PD-002 — Anchor=Route + StubProvider แทนการมี prototype tree แยก

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | ทั้ง project · สถาปัตยกรรม |
| สรุป | ไม่มีโฟลเดอร์ prototype แยก — story ผูกกับ route จริงใน `src/` โดยใช้ StubProvider เป็นข้อมูลจำลอง |

**บริบท:** UOMS มี `prototypes/` แยกจาก `src/` เพื่อให้ PO validate UI กับผู้ใช้ก่อนที่ dev จะลงมือ
project นี้คนเขียน spec กับคนเขียนโค้ดคือคนเดียวกัน การทำ UI สองรอบจึงเป็นงานซ้ำ

**การตัดสินใจ:** story ทุกใบผูกกับ **route จริง** ใน `src/app/` และเลือก **data mode** ได้สองแบบ:
`stub` (ข้อมูลจำลองแบบ offline ผ่าน `StubProvider` ซึ่ง implement สัญญา `PriceProvider` เดียวกับของจริง)
หรือ `live` (adapter จริง) หลักการ Anchor เปลี่ยนจาก "ต้นแบบถูกเสมอ" เป็น **Anchor=Route**:
เมื่อ spec กับ route ไม่ตรงกัน ให้ตัดสินว่าฝั่งไหนถูกแล้วแก้อีกฝั่งใน session เดียวกัน — ห้ามปล่อยให้ต่างกัน

**เหตุผล:** StubProvider ให้ประโยชน์เดียวกับ prototype (เดินจอได้ก่อนมีข้อมูลจริง, เดโมได้ทุกเมื่อ,
ไม่พึ่ง network) โดยไม่ต้องสร้าง UI สองชุด และเพราะมันใช้สัญญาเดียวกับ provider จริง โค้ดที่เขียนตอน stub
คือโค้ดที่จะ ship จริง ไม่ใช่ของทิ้ง

**ผลที่ตามมา:** R9 ของ skill เปลี่ยนจาก "mock limitation" เป็น **"stub limitation"** — ทุกอย่างที่
StubProvider ไม่จำลอง (rate limit, สัญลักษณ์ที่ไม่มีจริง, ความลึกข้อมูล, เน็ตช้า) ต้องเขียนกำกับในการ์ด
ว่าเป็นเรื่องของข้อมูลจริง

### PD-003 — Governance แบบเบาก่อน (ไม่ port สคริปต์ guard ของ UOMS)

| ช่อง | ค่า |
| --- | --- |
| วันที่ | 2026-07-29 |
| สถานะ | ✅ Final |
| ขอบเขต | ทั้ง project · governance |
| สรุป | เริ่มด้วย decision log ไฟล์เดียว + guard มาตรฐาน (lint/tsc/vitest/build) แล้วค่อยเพิ่มสคริปต์เมื่อเจ็บจริง |

**บริบท:** UOMS มีสคริปต์ governance ครบชุด (`pd:claim`, `pd:index`, `check:decision-log`,
`check:story-rbac`, `check:estimate-lock`, `check:validation-codes`, …) ซึ่งมีค่ามากแต่เกิดจากความเจ็บ
สะสมของทีมหลายคนหลาย session พร้อมกัน project นี้ยังไม่มีเงื่อนไขนั้น

**การตัดสินใจ:** governance ตั้งต้นประกอบด้วย (1) `docs/product/decision-log.md` ไฟล์เดียว append-only
เลขรันมือ (2) `docs/product/_shared/validation-glossary.md` เป็นทะเบียนข้อความ error (3) guard คือ
`npm run lint` + `npx tsc --noEmit` + `npx vitest run` + `npm run build` + การเดิน route จริง
สคริปต์ตรวจเอกสารจะเพิ่ม **เมื่อ pattern ความผิดพลาดเดิมเกิดครั้งที่ 2** โดยบันทึกไว้ที่
`.claude/skills/_retro/journal.md` ก่อนเสมอ (ratchet)

**เหตุผล:** สคริปต์ที่เขียนก่อนเจอปัญหาจริงมักจับผิดจุด และเพิ่มต้นทุนการ setup ตั้งแต่ session แรก
ซึ่งขัดกับเป้าหมาย "มีของ demo ให้เร็ว" — แต่การจดบทเรียนไว้ตั้งแต่แรกไม่มีต้นทุน จึงทำตั้งแต่วันนี้

**ผลที่ตามมา:** ตาราง Guards ใน SKILL.md ระบุเฉพาะคำสั่งมาตรฐาน; retro รอบ S8/S14/S20 คือจุดที่
ทบทวนว่าถึงเวลาเพิ่มสคริปต์หรือยัง
